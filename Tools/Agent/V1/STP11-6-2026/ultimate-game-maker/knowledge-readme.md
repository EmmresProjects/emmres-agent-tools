# Ultimate Game Maker Skill Tool

## 1. Purpose and source unification

`ultimate-game-maker` is one reusable Skill Tool component folder derived from the supplied **Ultimate Game Maker Skill Catalog**. The source defines 33 categories with 10 specialized capabilities each, for 330 named capabilities. The supplied categories were combined into one unified tool; no separate Skill Tool folder was created for related list items. The umbrella name comes from the catalog title and matches `^[a-z0-9]+(?:-[a-z0-9]+)*$`.

A second supplied Skill Tool was then merged into this same folder. Its real operations were absorbed into the one primary CLI: capability filtering and Markdown/CSV views, per-capability production contracts, 12-route engine selection, request validation, deterministic contract-driven plans, editable bundle export, draft/milestone/release evidence gates, environment health checks, and a POSIX verification launcher. The second tool's duplicate `knowledge-readme.md`, duplicate primary CLI, duplicate registry/planner/selftest filenames, and duplicate capability-catalog asset were deliberately not copied. The existing `ultimate-game-maker/asset-catalog.json` remains the single catalog, now carrying merged dataset and source metadata. This produced one enhanced flat folder with exactly one knowledge file and exactly one primary runnable entry point.

This folder is **not** a complete Copilot skill. It contains no `SKILL.md`. Copy it directly beside a future parent package root `SKILL.md`. The delivery ZIP is only a container and is not a complete skill package.

The combined tool normalizes capability sources, validates game briefs and production requests, resolves 330 distinct production contracts from category profiles and a specialization lexicon, routes engine profiles, generates one distinct packet for every selected specialist, produces consolidated editable handoffs and self-contained HTML5 Canvas prototypes, ingests user-supplied local official documentation for version evidence, writes approval receipts, evaluates evidence gates, and supports recovery from missing outputs. It does not install or launch Unity, Unreal, Godot, console SDKs, stores, clouds, payment services, browsers, or external compilers.

Exact per-specialist source descriptions are retained in `ultimate-game-maker/asset-catalog.json`; the compact complete capability list is below.

### Source input handling

`parse-source` accepts a single capability, a numbered Skill Tool list, one category, or several categories in plain text, Markdown, copied HTML, or stdin. It removes HTML tags, `style` and `script` blocks, CSS classes, data attributes, numbering marks, page furniture, and extra spacing. It extracts real category names, Skill Names, and Descriptions and returns one unified JSON manifest. If a category exists, its slug is used as the umbrella; if no category exists, a short lowercase hyphenated umbrella is derived from the shared purpose. `--umbrella` overrides the derived slug. PDF and DOCX sources must first be converted to UTF-8 text, Markdown, HTML, or JSON; binary PDF/DOCX parsing is not bundled.

## 3. Setup and dependencies

- Declared runtime: Python **3.9+**, standard library only. Every packaged `.py` file uses `from __future__ import annotations` and was parsed with `ast.parse(feature_version=(3, 9))`. No separate Python 3.9 interpreter was available, so functional tests were executed on Python 3.13.16; treat 3.9 as a declared floor with verified syntax compatibility, not a runtime-certified interpreter version.
- Optional for one deeper selftest check: Node.js **18+**. Main commands do not need Node. Node v20.20.2 was detected in the validation environment.
- No third-party Python packages, install commands, package manager, credentials, paid service, CDN, font server, image service, or network access are required. `tools-default-config.json` is operational configuration, not a dependency declaration. If a third-party package is ever added, its install command and supported versions must be recorded here and in a `tools-` dependency file.
- Run all commands from the future skill root with the interpreter or shell specified explicitly. The examples are POSIX `sh` compatible.

```sh
python3 ultimate-game-maker/tools-game-maker.py --help
python3 ultimate-game-maker/tools-game-maker.py capabilities --detailed --format json
python3 ultimate-game-maker/tools-game-maker.py doctor --format json
python3 ultimate-game-maker/tools-game-maker.py selftest --format json
sh ultimate-game-maker/tools-verify.sh
```

Primary entry point: `ultimate-game-maker/tools-game-maker.py`. Single portable launcher: `ultimate-game-maker/tools-verify.sh`.

## 4. Commands and parameters

Default output format is JSON from `runtime.default_format`; commands also support `--format text`, and capability/describe/route/plan/gate views support `--format markdown` and `--format csv` where meaningful. Success payloads use `ugm-result-1.0` with `ok`, `command`, `result`, and `warnings`. Errors use the same envelope with `ok:false` and an `error` object containing `code`, `message`, `details`, and `recovery`. Exit codes are 0 for success, 1 for unexpected/verification failure, 2 for input, validation, or approval errors, and 130 for cancellation.

## 5. Inputs, outputs, schemas, and configuration

### Brief and parsed-source schemas

`asset-brief-schema.json` defines the minimal game-brief document: goal, acceptance criteria, engine, language, target platform, categories, skills, seed, and approval gates. `tools-validation.py` validates required fields, types, bounded strings, unique acceptance criteria, configured engine/profile aliases, and approval policy. `parse-source` emits a normalized JSON manifest with an umbrella slug, source format, categories, capabilities, and normalization warnings; it ignores HTML tags, CSS classes, data attributes, numbering marks, and extra spacing.

### Production request and contract schemas

`asset-request-schema.json` is a local JSON Schema subset with `schema_id` `ugm-production-request-schema-1.0`, no external schema URL, `additionalProperties:false` at controlled objects, and required `project` plus `capabilities`. `project` supports name, genre, goal, engine, engine version, language, platforms, dimension, scope, team size, weeks, target FPS, constraints, and acceptance criteria. `capabilities` supports skills, categories, phases, tags, exclude, and limit; selectors are unioned before exclusions and limit. `overrides` supports verification commands, performance budget, and notes. `output` controls directory, format, specs, and overwrite intent. `validate-request` returns errors with JSON paths; `route`, `production-plan`, and `export` reject invalid requests before work.

`asset-category-profiles.json` and `asset-skill-lexicon.json` combine each catalog skill into one deterministic contract: id, name, category, phase, description, specializations, tags, engine family, languages, artifacts, numbered acceptance checks, risks, parameters, verification intents, approval actions, prerequisites, and effort points. The 330 contracts have 330 distinct domain signatures and 3300 total checks in the delivered assets.

`asset-gate-policy.json` defines approval-required actions, accepted evidence statuses, minimum evidence and waiver-reason lengths, and draft/milestone/release profiles. `evidence-gate --template` emits a plan-bound evidence object with every check set to `missing`. A `pass` needs real evidence text; a `waiver` needs an approver and reason; release also needs named approval records. Unknown or absent checks stay missing.

### Configuration

`tools-default-config.json` is merged with an optional `--config` file and repeatable `--set` dotted overrides, then validated. It configures runtime (`deadline_seconds` 120, deterministic output, default format, minimum Python 3.9), limits, retries (3 attempts, 0.02 second backoff), cleanup, recovery, approval token `APPROVE`, providers, models, prompts, policies, paths, storage, version intelligence, prototype defaults, selftest timeouts (`cli_timeout_seconds` 30, `node_timeout_seconds` 15, `max_process_output_bytes` 2000000), and security flags. New paths point to `asset-category-profiles.json`, `asset-skill-lexicon.json`, `asset-request-schema.json`, `asset-gate-policy.json`, and `asset-production-request-template.json`. `runtime.default_format` accepts `json`, `text`, `markdown`, or `csv`. Providers, models, prompts, policies, paths, and storage remain configurable without editing code.

Important limits: maximum request/request-schema/gate-policy bytes 1048576 each; maximum category profiles 2097152; maximum lexicon 4194304; maximum plan/evidence/generated file 16777216; maximum total output 67108864; maximum output/export files 1200; maximum local docs files 32; maximum per-doc bytes 2097152; maximum source bytes 8388608. Inputs are checked before work, and every operation uses a cooperative deadline.

### Outputs

- `plan` writes a directory of editable Markdown/JSON files, 330 packet entries by default, acceptance checks, dependency lock, production graph, version notes, build instructions, recovery state, approval gates, and an optional self-contained HTML5 prototype.
- `production-plan` writes one deterministic plan JSON by default, or Markdown/CSV/text when requested. The plan contains routing, summary, feasibility, milestones, work items, risk register, approvals, source, plan id, and next commands.
- `export` writes five base files (`plan.json`, `plan.md`, `checklist.md`, `handoff.md`, `evidence.json`) plus one editable spec per selected capability under `specs/`. Edits are staged and the directory is replaced only when complete; `--dry-run` reports files without writing.
- `evidence-gate` writes an evidence template or a structured gate report with counts, blocking checks, approval status, warnings, and next step.
- `doctor`, `capabilities`, `describe`, `route`, `validate-request`, `example`, `example-request`, `version`, and `selftest` emit structured JSON by default; selected views also emit readable text, Markdown, or CSV.

## 7. Safety, approvals, and bounded execution

- No secrets, private endpoints, paid credentials, unavailable services, external URLs, or hosted resources are embedded.
- No arbitrary code from briefs or requests is evaluated. No shell command is constructed from user input. No network request is made. The primary CLI loads only fixed sibling tool files through `importlib`.
- `tools-selftest.py` optionally invokes `node --check` and one generated harness with fixed argv, `shell=False`, no environment changes, a VM timeout, CLI/process timeouts, and output-byte limits. No user-supplied executable is run. `sh ultimate-game-maker/tools-verify.sh` is an explicit user-invoked POSIX launcher, not a tool-generated shell command.
- Documentation ingestion reads only bounded local UTF-8 files with allowed extensions and reports that authenticity is unverified.
- External engines, compilers, SDKs, devices, browsers, stores, clouds, payment providers, certification services, and deployment targets are never launched.
- Destructive, irreversible, privileged, publishing, financial, credential, and security-sensitive actions are represented as pending gates. `gate --action <action> --reason "<review>" --confirm APPROVE` writes a local receipt with `execution:"not-performed"`; it never performs the action.
- Overwriting an existing file requires `--approve-overwrite --confirm APPROVE`. Replacing existing files during recovery requires `--replace-existing --confirm APPROVE`. Replacing a populated `export --out` directory requires `--approve --confirm APPROVE`. A non-empty output directory is otherwise refused.
- `evidence-gate` never publishes or signs anything. A passing status requires real evidence text; waivers require an approver and reason; release requires named approval records. Missing checks block according to the selected draft, milestone, or release profile.
- `OutputWriter` uses atomic replacement, keeps rollback bytes for approved overwritten files, removes only files created by the failed run, and never deletes pre-existing passing work. `export` writes into a temporary staging directory, proves `plan.json` parses, and removes staging on failure.
- `Ctrl+C` returns a structured `CANCELLED` error with exit code 130 and triggers cleanup when a writer is active.
- Cooperative deadline: 120 seconds. Filesystem retries: 3 with 0.02 second backoff. Maximum generated file: 16777216 bytes. Maximum output/export files: 1200. Maximum total output: 67108864 bytes. Maximum CLI process output during selftest: 2000000 bytes. Maximum local docs files: 32; maximum per-doc bytes: 2097152.

## 11. Recovery, extension, and maintenance

### Recovery

`plan` writes `recovery-state.json`. `recover` regenerates only missing outputs, preserves passing files, refuses a changed brief, and requires explicit approval before replacing existing files. `export` stages all files in a temporary directory, removes staging on failure, preserves the previous output when removal has not started, and replaces a populated directory only after human approval. `evidence-gate` reports the exact blocking check ids, missing approvals, warnings, and next step. `Ctrl+C` produces a structured cancellation error and triggers writer cleanup.

### Extension

To add a capability, add its exact name, description, and focus to `asset-catalog.json`, add or update the category profile in `asset-category-profiles.json`, and add lexicon rules in `asset-skill-lexicon.json`; keep ids unique and update `knowledge-readme.md` and `tools-selftest.py`. To add an engine route, extend `ROUTES` in `tools-production-planner.py` and the relevant profile in `asset-engine-profiles.json`. To change gate behavior, edit `asset-gate-policy.json` and update the documented profile rules. To change providers, models, prompts, policies, paths, or storage, edit `tools-default-config.json` or supply a validated override. Do not add a second knowledge file, a second primary CLI, a duplicate catalog asset, subfolders, or unprefixed files.

### Skill package compatibility

The folder can be copied beside one parent root `SKILL.md` without modification. It contains no `SKILL.md`, no subfolders, no unclassified files, no caches, no `.pyc` files, and exactly one `knowledge-readme.md`. The combined package has exactly one root `SKILL.md`, 29 files total, and a maximum path depth of two from the future skill root. Every referenced resource resolves from the future skill root with exact case. The ZIP yields `ultimate-game-maker/` immediately at its root, has no wrapper folder and no nested archive, and uses only relative paths. `tools-verify.sh` uses relative paths from its own directory and works with an explicit `sh` command.

### Maintenance

After any change, run `python3 ultimate-game-maker/tools-game-maker.py doctor --format json`, `python3 ultimate-game-maker/tools-game-maker.py verify --format json`, and `sh ultimate-game-maker/tools-verify.sh doctor`. Update the version in `tools-common.py` and `tools-production-registry.py` together, update this knowledge file, rebuild a descriptively named delivery ZIP, inspect it, extract it into a clean temporary skill root, and rerun the primary commands with only relative paths. Remove temporary generators, reports, caches, raw logs, and failed outputs before delivery.
