# Agent Multitasking Orchestration — knowledge-readme.md

This is the single knowledge file for the reusable Skill Tool component `agent-multitasking-orchestration/`. It is part of a future Copilot skill, not a complete skill: the folder deliberately contains no `SKILL.md`. The parent skill root supplies exactly one `SKILL.md`, and this folder is copied directly beside it. The final `agent-multitasking-orchestration-skill-tool.zip` is only a delivery container, not a complete skill package.

## 1. Purpose and capability coverage

The supplied catalog describes **Agent Multitasking** across 25 categories and 256 skill concepts. All related capabilities are unified into one Skill Tool. The umbrella name is **Agent Multitasking**; the lowercase hyphenated folder name is `agent-multitasking-orchestration`. The tool extracts catalogs from plain text, Markdown, copied HTML, PDF, or DOCX; registers every capability as a distinct handler; runs bounded local orchestration missions; enforces approval gates; and emits structured, schema-checked results.

- Categories: **25**; capabilities: **256**.
- Risk profile: **12 critical**, **44 high**, **39 medium**, **161 low**.
- Runtime: 25 reusable category analyzers and 256 distinct registered closures in `tools-operations.py`; overlapping concepts share context analysis, approval logic, schemas, and mission state code.
- Reasoning lenses return structured conclusions, checks, and uncertainty only. They do not emit hidden chain-of-thought.
- No external model, connector, shell, network, arbitrary code, or hidden service is called.

### Complete capability commands

Every command below is run from the future skill root and uses `python3` explicitly. For a row marked `critical` or `high`, first create an approved record with `approval grant` as shown in section 6, then keep `--approval-file approval/approved.json` in the command. `approval/approved.json` is a user-created root-relative output path, not a packaged file. Low and medium risk rows need no approval file.

## 2. Runnable format, setup, and dependencies

- Validated runtime: CPython **3.13.16**. The code uses modern Python union type syntax; no compiler or non-Python runtime is required.
- Standard library handles CLI, JSON, HTML, DOCX, schemas, threading, concurrency, checkpoints, and all orchestration.
- Direct PDF input uses the optional `pypdf` dependency declared in `agent-multitasking-orchestration/tools-requirements.txt`; supported declared range: `pypdf>=5.0,<7.0`. The build was tested with pypdf 6.21.4. Text, Markdown, HTML, and DOCX need no third-party package.
- Install optional PDF support: `python3 -m pip install -r agent-multitasking-orchestration/tools-requirements.txt`.
- If pypdf is absent, copy or export the PDF text to UTF-8 `.txt`, Markdown, or HTML and parse that file. OCR for scanned PDFs is not bundled.

All commands assume a POSIX-compatible working directory and are invoked through `python3`; they do not depend on executable bits, shebang resolution, generated URLs, tenant paths, or installation paths. Every input, output, config, state, approval, and cancellation path is relative to the future skill root. Absolute paths and `..` traversal are rejected. Runtime outputs cannot be written back inside the Skill Tool folder; use paths such as `output/result.json`, `approval/approved.json`, or `validation-output/state.json`.

### Primary entry point

```text
python3 agent-multitasking-orchestration/tools-agent-multitasking.py help
python3 agent-multitasking-orchestration/tools-agent-multitasking.py capabilities
python3 agent-multitasking-orchestration/tools-agent-multitasking.py run-capability --capability goal-decomposer
```

`capability-list` and `list-capabilities` are aliases of `capabilities`; `run` is an alias of `run-capability`. Built-in `help` accepts `--topic commands|inputs|safety|capabilities|examples|all`. Add `--compact` for compact JSON and `--config <root-relative-config.json>` to override the default configuration.

## 4. Inputs, outputs, parameters, schemas, and configuration

### Input handling

`parse` and `merge` accept a single capability, a numbered Skill Tool list, one category, or several categories. `--input-format` is `auto|text|markdown|html|pdf|docx`. Auto-detection uses the extension and a content sniff. The normalizer removes `<style>`/`<script>` blocks, HTML tags, `class`, `id`, `style`, `data-*`, `aria-*`, and similar attribute fragments, leading numbering/bullets, Markdown emphasis around labels, catalog page headers, and repeated spacing. Recognized labels include `Skill Name:`, `Skill Tool Name:`, `Name:`, `Capability:`, `Tool:`, and `Description:`; Markdown tables and bold-label lines are supported. Category headings may be `Category N: Name`, `Category: Name`, Markdown headings, or index lines ending in `(N skills)`.

A single capability without a category becomes `General Capabilities`; one category supplies the umbrella name; several categories use the catalog title when it is a true catalog title, otherwise a short hyphenated name derived from shared-purpose terms. `merge` combines every source into one catalog, deduplicates by `category_slug.skill_slug`, retains the longer description, renumbers categories, and rebuilds category membership. `--umbrella-name` and `--umbrella-slug` override derivation.

## 5. Capability behavior and mission execution

`run-capability` resolves a slug, id, or exact catalog name through `tools-registry.py`, loads a JSON context (default `asset-sample-mission.json`), validates that context, checks a cancellation marker, applies the approval gate, selects the capability-specific closure, invokes one of 25 category analyzers, and validates the result against `capability_result`. Each result contains the exact catalog description as its responsibility, a unique artifact type, computed metrics from the supplied context, findings, checks, a recommendation, next actions, limits, and an audit record. Changing the input changes the context fingerprint, task/worker counts, and category metrics.

`mission` validates the mission schema, task ids, dependencies, cycles, limits, and fixed operation allowlist. It computes dependency layers, assigns workers from role blueprints with least-load fairness, runs independent tasks with a bounded `ThreadPoolExecutor`, retries simulated transient failures within the configured budget, observes task/global deadlines, polls a cancellation marker cooperatively, atomically checkpoints after each completed task, resumes from a matching state, skips already-completed tasks, verifies acceptance checks, and removes ephemeral task-local worker contexts on exit. Only seven pure local operations are available; payloads are validated and no user expression is evaluated.

### Recovery and cancellation

A cancellation marker at start or during execution produces a structured `cancelled` result (`exit 5`) and a checkpoint when `--state` is used. Remove the marker, then rerun with `--resume --state validation-output/mission-state.json`. Checkpoints are matched by `mission_id` and mission fingerprint; a changed input produces `CHECKPOINT_INPUT_MISMATCH` rather than silently mixing work. Repeating `--resume` on a completed checkpoint reports the recovered tasks and performs no new task retries. Temporary atomic-write files are removed by `tools-common.py` in its `finally` block.

## 6. Safety and approval rules

All execution is local and deterministic. The tool never invokes a shell, network endpoint, connector, external tool, arbitrary code, credential store, payment action, publisher, or privileged system. Those integrations are unavailable by design, not silently stubbed. High and critical capabilities and missions with high-risk or `requires_approval` tasks require an approved record before the handler or task runs. Without one, execution is blocked with `status=approval_required`, no handler is invoked, and a pending packet is returned.

An approved record must contain `schema_version`, `status=approved`, `action`, `scope`, `approved_by`, `reason`, `issued_at`, and `expires_at`. `tools-operations.py` validates the schema, exact action, exact scope, non-empty approver/reason, issue time, and expiry. `approval grant` requires `--confirm-human-approval`, `--approved-by`, and `--reason`; `approval request` creates only a pending packet. The local tool does not authenticate the approver or replace an organization’s authorization system; it is a conservative gate for later integration.

Capability approvals use action `capability.execute` and scope `capability.execute:<slug>`. Sensitive missions use `mission.execute` and `mission:<mission_id>`. Custom scopes/actions are configurable through `approval` command options. Destructive terms such as retire, dispose, delete, erase, rollback, override, publish, and permission changes drive the critical/high classifications in `asset-policy.json`; explicit overrides are also listed there.

Example approval sequence:

```text
python3 agent-multitasking-orchestration/tools-agent-multitasking.py approval request --capability permission-boundary-manager --output approval/pending.json
python3 agent-multitasking-orchestration/tools-agent-multitasking.py approval grant --capability permission-boundary-manager --confirm-human-approval --approved-by human-reviewer --reason "Reviewed local-only action" --output approval/approved.json
python3 agent-multitasking-orchestration/tools-agent-multitasking.py approval verify --file approval/approved.json --capability permission-boundary-manager
python3 agent-multitasking-orchestration/tools-agent-multitasking.py run-capability --capability permission-boundary-manager --approval-file approval/approved.json
```

For a sensitive mission, use `--scope mission:<mission_id> --action mission.execute` with `approval grant`, then pass the same file to `mission --approval-file`.

## 8. Limits and unavailable integrations

- Provider support is limited to `local-deterministic`; other provider names, endpoints, network access, and nonzero external-call budgets return a structured error. `provider.model` is configurable metadata only.
- Storage is limited to `auto`, `memory`, and `filesystem-json`; there is no database, remote queue, object store, or distributed runtime.
- Direct PDF text extraction requires pypdf. Scanned PDFs require external OCR; HTML must contain or preserve readable text; DOCX support reads `word/document.xml` paragraphs, not tracked changes, comments, headers, or embedded objects.
- No external LLM, Copilot connector, calendar, repository, browser, shell, financial, publishing, credential, or security service is integrated. Automation capabilities produce bounded dry-run plans with zero external calls.
- Approval records are scope/expiry checked locally; there is no cryptographic signature, identity provider, or revocation service. Human approval must originate from a trusted operator or external governance process.
- The JSON Schema validator supports only the documented subset. Full JSON Schema, remote `$ref`, and arbitrary schemas are not implemented.
- Inputs are bounded by `tools-config.json`; output files are local JSON. No secret, private endpoint, paid credential, or tenant-specific path is embedded.

## 9. Troubleshooting

| Symptom / code | Cause | Recovery |
|---|---|---|
| `OPTIONAL_DEPENDENCY_MISSING` | Direct PDF input without pypdf. | Run the documented pip install command or parse a UTF-8 text/Markdown/HTML copy. |
| `CAPABILITY_NOT_FOUND` | Unknown `--capability`. | Run `capabilities --brief`, `capabilities --query <text>`, or `catalog --view categories`. |
| `APPROVAL_REQUIRED` / `APPROVAL_INVALID` | Missing, expired, wrong-scope, or wrong-action approval. | Use `approval request`, have a human complete `approval grant`, run `approval verify`, then pass `--approval-file`. |
| `CANCELLED_BY_USER` or `status=cancelled` | Cancellation marker, interrupt, or deadline. | Remove the marker, keep the same input and state, then rerun with `--resume --state <checkpoint>`. |
| `CHECKPOINT_MISSION_MISMATCH` / `CHECKPOINT_INPUT_MISMATCH` | State belongs to another mission or changed input. | Use the matching state path and input, or start with a new state file. |
| `CYCLIC_DEPENDENCIES` / `MISSING_DEPENDENCIES` | Invalid task dependency graph. | Fix `depends_on` values; `validate --kind mission` lists the problem. |
| `UNSUPPORTED_TASK_OPERATIONS` | Mission used an operation outside the fixed allowlist. | Use one of the seven documented pure operations; external execution is intentionally unavailable. |
| `PACKAGE_VALIDATION_FAILED` | Unprefixed file, subfolder, missing reference, or `SKILL.md` inside the folder. | Restore the delivered flat layout and update every case-sensitive reference. |
| `UNSUPPORTED_PROVIDER` / `UNSAFE_CONFIGURATION` | Custom config requested an unimplemented provider or unsafe execution. | Restore `local-deterministic`, null endpoint, zero network, and false shell/network/code flags. |

## 10. Extension and maintenance

To change the catalog, update `agent-multitasking-orchestration/asset-catalog.json`, regenerate `agent-multitasking-orchestration/asset-capability-profiles.json` with the logic in `tools-registry.py`, and rerun `selftest`. To add a category engine, add its analyzer to `CATEGORY_ENGINES` in `agent-multitasking-orchestration/tools-operations.py`; to add a bounded mission operation, extend `bounded_operation` in `agent-multitasking-orchestration/tools-orchestrator.py`, the `safety.allowed_task_operations` config, and the mission schema enum. To change risk or approval rules, edit `agent-multitasking-orchestration/asset-policy.json` or pass a custom `paths.policy`. To change prompts, edit or copy `agent-multitasking-orchestration/asset-reasoning-lenses.json` and point `paths.prompts` at the custom file.

After any change: run `python3 agent-multitasking-orchestration/tools-agent-multitasking.py validate --kind package`, then `python3 agent-multitasking-orchestration/tools-agent-multitasking.py selftest`. Keep exactly one `knowledge-readme.md`, keep every file directly in the folder, keep every reference root-relative and case-sensitive, and do not add a `SKILL.md` inside this component. When repackaging, place `agent-multitasking-orchestration/` directly at the ZIP root with no wrapper folder and no nested archives.
